| A12 | 🐞 **BUG — `CreateAsset`, `CreateLocation`, `CreateHold` and `PostMovement` all honor a caller-supplied `id`, contradicting their own doc comments, and a duplicate id 500s instead of a clean conflict.** Driven through the real `routes.Routes(am)` mux (sqlite, in-process): `POST /assets {"id":"attacker-chosen-asset-id","name":"probe","tracking_mode":"fungible"}` → `201 {"id":"attacker-chosen-asset-id",...}` — the caller's literal string becomes the row's primary key, when `models/asset.go`'s own `ID` doc comment says "Set by the backend on creation; callers should leave it empty in create requests." `asset.go`'s `CreateAsset` never clears `a.ID` before `gormstore.AssetToRow(a)`, and `AssetRow.BeforeCreate` only mints a UUID `if r.ID == ""`. The identical gap, with the identical doc-comment contradiction, exists in `location.go`'s `CreateLocation`, `hold.go`'s `CreateHold`, and `movement.go`'s `PostMovement` — confirmed by the same probe against `POST /locations`, `POST /holds`, and `POST /movements`. Re-`POST`ing the same id a second time (`/assets` demonstrated) hits the sqlite/Postgres primary-key unique constraint and 500s (`errors.go` has no duplicate-id sentinel at all — no `ErrDuplicateID`/`ErrConflict` equivalent — so `writeAssetErr`'s default arm answers an opaque `500 {"error":"internal error"}`). Same bug class already found and fixed/pinned elsewhere in this fleet: `mwanachama-backend-agency`'s AG21, `mwanachama-backend-custody`'s DEV-1695/1696, and `mwanachama-backend-taskmanager`'s W11 (same integration-test sweep, same day) — this repo has neither the ID-clearing fix nor either sibling's duplicate-id classifier (`ErrDuplicateID` in actor, `ErrConflict` in comm/custody). **Fix location**: clear `.ID` at the top of `CreateAsset`/`CreateLocation`/`CreateHold`/`PostMovement`, before building the row; separately, add a duplicate-id sentinel (matching actor's `classifyDuplicateID`/comm's `classify` shape) and map it to 409 in `writeAssetErr`/the other three `write*Err` functions. | 📋 | Found 2026-09-16 by the fleet integration-test sweep (loophole catalogue #3/#9: a caller-controlled identity field the server's own docs say it should own). | A13 | 🐞 **BUG — `CommitHold` and `ReleaseHold` race: two concurrent callers on the same reserved Hold can both succeed, and `ReleaseHold`'s own 200 response is silently contradicted moments later.** Driven through the real `routes.Routes(am)` mux behind `httptest.NewServer` with two real `*http.Client` requests fired concurrently — `POST /holds/{holdID}/commit {"quantity":5,"kind":"departed","performed_by":"committer"}` racing `POST /holds/{holdID}/release` on the same freshly-created, still-`reserved` Hold. Both `hold.go`'s `CommitHold` and `ReleaseHold` follow the identical unguarded read-then-write shape: `GetHold` (a plain `SELECT`), a Go-level `if hold.Status != models.HoldStatusReserved` check, then an unconditional `UPDATE ... WHERE id = ?` with **no `AND status = 'reserved'` guard and no `RowsAffected` check** — so two callers whose reads both land before either write can both pass the Go-level check and both write, even though `models.HoldStatus.CanTransitionTo`'s own doc says every transition out of `reserved` is terminal (a Hold is meant to be committed or released at most once). Repeated across 40 fresh holds per run (three runs: 13/40, 32/40, 24/40 iterations landed both requests as HTTP 200) — and because `CommitHold` does substantially more work first (it posts a real Movement via `PostMovement` before touching the Hold row), its write almost always lands last: in every single one of those "both 200" iterations across all three runs (13/13, 32/32, 24/24), the persisted Hold ended up `status="committed"` even though the concurrent `ReleaseHold` call's own response body said `"released"` with no error — a caller trusting its own success response is being told something the database has already stopped agreeing with. **Fix location**: give both `hold.go`'s `CommitHold` and `ReleaseHold` a compare-and-swap write — `Updates(...).Where("id = ? AND status = ?", hold.ID, models.HoldStatusReserved)`, checking `RowsAffected` and returning `ErrInvalidHoldStatusTransition` on 0 — the same shape `mwanachama-backend-git`'s `advanceBranchHead` already uses for its own CAS guard against a comparable race. | 📋 | Found 2026-09-17 by the fleet integration-test sweep (loophole catalogue #8: second-actor isolation / a race between the expiry watchdog's `ReleaseHold` sweep and a normal `CommitHold` call, or two operators). Pinning test committed in `routes/a13_hold_commit_release_race_test.go` (`TestPinsA13_ConcurrentCommitAndReleaseBothSucceedOnSameHold`) — asserts the *current* broken behavior (at least one of 40 concurrent-race iterations lands both requests as HTTP 200), fails loudly if the race stops reproducing so it can't silently start passing for the wrong reason once fixed; its own comment documents what to rewrite it to assert once A13 lands (at most one of the two concurrent requests succeeds). `go test ./...`, `go test -tags=integration ./...`, and `go test -race ./...` all green with it added — the race is a real business-logic TOCTOU, not a Go data race, so `-race` does not (and is not expected to) flag it itself. |
| A14 | 🐞 **BUG — `UpdateAsset`/`UpdateLocation` each race their own `DeleteAsset`/`DeleteLocation`: a concurrent soft-delete does not stop the update's write, so the racing update's new content silently lands on an already-deleted row.** Driven through the real `routes.Routes(am)` mux behind `httptest.NewServer`, two real `*http.Client` requests fired concurrently per iteration — `PATCH /assets/{assetID} {"name":"raced-update"}` racing `DELETE /assets/{assetID}` on the same freshly-created asset (and separately, `PATCH /locations/{locationID}` racing `DELETE /locations/{locationID}`). Both `asset.go`'s `UpdateAsset` and `location.go`'s `UpdateLocation` read the current row through `GetAsset`/`GetLocation` (`WHERE id = ? AND deleted = false`) but then write through a bare `Updates(map[string]any{...}).Where("id = ?", id)` with **no `deleted` guard on the write at all** — so a `DeleteAsset`/`DeleteLocation` that flips `deleted=true` in the gap between the update's own read and its own write is invisible to that write, which still applies the caller's new Name and returns HTTP 200/nil-error. Repeated across 200 fresh rows per entity: Asset — 197-199/200 iterations landed both PATCH and DELETE as success, and in every one of those the persisted row was confirmed `deleted=true` with `name="raced-update"` (read via a raw `SELECT`, since `GetAsset`/`ListAssets` would filter the row out and report nothing). Location — 199/200 iterations, 199/199 of those confirmed the same shape. This race is far wider than A13's (no extra work happens between the delete's own read and write, unlike `CommitHold`'s `PostMovement` detour), which is why it reproduces on almost every iteration rather than roughly half. **Fix location**: give both `UpdateAsset`'s and `UpdateLocation`'s writes a compare-and-swap guard — `Updates(...).Where("id = ? AND deleted = ?", id, false)`, checking `RowsAffected` and returning `ErrAssetNotFound`/`ErrLocationNotFound` on 0 rows affected — the same shape already recommended for A13 and already used by `mwanachama-backend-git`'s `advanceBranchHead`. | 📋 | Found 2026-09-19 by the fleet integration-test sweep (loophole catalogue #8/#2: a second actor deleting while the first is mid-update; a derived/soft-delete state one write path checks and another ignores). Two pinning tests committed in `routes/a14_update_delete_race_test.go` (`TestPinsA14_UpdateAssetCanWriteIntoAnAlreadyDeletedRow`, `TestPinsA14_UpdateLocationCanWriteIntoAnAlreadyDeletedRow`) asserting the *current* broken behavior (at least one of 200 iterations lands a racing update's content on an already-deleted row) — each fails loudly if the race stops reproducing, and each documents in its own comment what to flip the assertion to once A14 lands (0 iterations). Widening note: the same shape was also found and filed in `mwanachama-backend-taskmanager` as W19 (`UpdateTask`/`DeleteTask`, same session); `mwanachama-backend-actor` was checked and ruled out (no `DeleteGroup`/`DeleteActor` method exists at all, so there is nothing for an edit to race — see that repo's own sweep log). `go test ./...` and `go test -tags=integration ./...` both green with these added. |
