| A15 | 🐞 **BUG — `NextCode` (`gormstore/codesequence.go`) reads the counter row then writes `next_number+1` with no CAS guard and no row lock, so two ordinary concurrent `Create<Type>` calls (`CreateAsset`/`CreateLocation`, everyday operations) can fail outright with a raw, unclassified database error.** `NextCode` does `SELECT ... WHERE entity_type = ?` (no `FOR UPDATE`/lock) to read `n`, computes `n+1` in Go, then `UPDATE ... SET next_number = <literal n+1> WHERE entity_type = ?` — no `WHERE next_number = ?` precondition, so nothing detects or serializes a second concurrent reader of the same `n`. Demonstrated directly against `AssetManager.CreateAsset` (`asset.go:66` calls this same helper inside its own transaction), firing 2 goroutines concurrently per iteration across 30 iterations on a shared-cache multi-connection in-memory sqlite database (`file::memory:?cache=shared`, `SetMaxOpenConns(4)` — this repo's own single-connection `:memory:` test convention fully serializes each `CreateAsset` call's whole transaction and cannot expose this race at all). Real output: **11/30 iterations (37%) had one of the two concurrent `CreateAsset` calls fail** with `CreateAsset: NextCode: database table is locked: database is deadlocked (6)` — a raw SQLite driver error propagated completely unwrapped to the caller, not any of this repo's own sentinels, for an operation (creating two unrelated fungible Assets) that has no legitimate reason to fail. This is the identical `gormstore/codesequence.go` shape independently found the same sweep in `mwanachama-backend-agency` (AG35) and `mwanachama-backend-actor` (ACT3), and also present verbatim in `mwanachama-backend-taskmanager` (filed there separately) — all four repos carry their own byte-for-byte copy of this helper (no shared package), so the same fix needs applying in each. Demonstrated fact is the SQLite failure mode above; the more severe theoretical failure mode on Postgres (an unconditional `UPDATE` with no precondition letting a second writer silently proceed once the first commits, producing two rows sharing the same Code, e.g. two Assets both `"A-5"`) was not demonstrated — this repo's own tests never stand up real Postgres — and is flagged as risk, not filed as a separately confirmed finding. Fix location: `gormstore/codesequence.go`'s `NextCode` — either a CAS write (`UPDATE ... SET next_number = ? WHERE entity_type = ? AND next_number = ?`, retried on `RowsAffected == 0`) or a row lock (`SELECT ... FOR UPDATE` on Postgres). | 📋 | Found 2026-09-21 by the fleet integration-test sweep, widening ACT3/AG35's finding into every sibling repo carrying the same copy-pasted `gormstore/codesequence.go`. No committed pinning test — the probe needed a non-standard shared-cache multi-connection sqlite setup (`file::memory:?cache=shared`, `SetMaxOpenConns(4)`) diverging from this repo's own single-connection test convention, and its result (a 37% failure *rate*, not a deterministic reproduction) is a probe finding, not a stable regression-guard shape; the real output quoted above is the reproduction. Probe file (`zz_probe_nextcode_race_test.go`) deleted per the sweep's own rule against leaving a probe file behind. `go build`/`go test ./...`/`go test -tags=integration ./...` all still clean (no product code touched). |
| A13 | 🐞 **BUG — `CommitHold` and `ReleaseHold` race: two concurrent callers on the same reserved Hold can both succeed, and `ReleaseHold`'s own 200 response is silently contradicted moments later.** Driven through the real `routes.Routes(am)` mux behind `httptest.NewServer` with two real `*http.Client` requests fired concurrently — `POST /holds/{holdID}/commit {"quantity":5,"kind":"departed","performed_by":"committer"}` racing `POST /holds/{holdID}/release` on the same freshly-created, still-`reserved` Hold. Both `hold.go`'s `CommitHold` and `ReleaseHold` follow the identical unguarded read-then-write shape: `GetHold` (a plain `SELECT`), a Go-level `if hold.Status != models.HoldStatusReserved` check, then an unconditional `UPDATE ... WHERE id = ?` with **no `AND status = 'reserved'` guard and no `RowsAffected` check** — so two callers whose reads both land before either write can both pass the Go-level check and both write, even though `models.HoldStatus.CanTransitionTo`'s own doc says every transition out of `reserved` is terminal (a Hold is meant to be committed or released at most once). Repeated across 40 fresh holds per run (three runs: 13/40, 32/40, 24/40 iterations landed both requests as HTTP 200) — and because `CommitHold` does substantially more work first (it posts a real Movement via `PostMovement` before touching the Hold row), its write almost always lands last: in every single one of those "both 200" iterations across all three runs (13/13, 32/32, 24/24), the persisted Hold ended up `status="committed"` even though the concurrent `ReleaseHold` call's own response body said `"released"` with no error — a caller trusting its own success response is being told something the database has already stopped agreeing with. **Fix location**: give both `hold.go`'s `CommitHold` and `ReleaseHold` a compare-and-swap write — `Updates(...).Where("id = ? AND status = ?", hold.ID, models.HoldStatusReserved)`, checking `RowsAffected` and returning `ErrInvalidHoldStatusTransition` on 0 — the same shape `mwanachama-backend-git`'s `advanceBranchHead` already uses for its own CAS guard against a comparable race. | 📋 | Found 2026-09-17 by the fleet integration-test sweep (loophole catalogue #8: second-actor isolation / a race between the expiry watchdog's `ReleaseHold` sweep and a normal `CommitHold` call, or two operators). Pinning test committed in `routes/a13_hold_commit_release_race_test.go` (`TestPinsA13_ConcurrentCommitAndReleaseBothSucceedOnSameHold`) — asserts the *current* broken behavior (at least one of 40 concurrent-race iterations lands both requests as HTTP 200), fails loudly if the race stops reproducing so it can't silently start passing for the wrong reason once fixed; its own comment documents what to rewrite it to assert once A13 lands (at most one of the two concurrent requests succeeds). `go test ./...`, `go test -tags=integration ./...`, and `go test -race ./...` all green with it added — the race is a real business-logic TOCTOU, not a Go data race, so `-race` does not (and is not expected to) flag it itself. |
| A14 | 🐞 **BUG — `UpdateAsset`/`UpdateLocation` each race their own `DeleteAsset`/`DeleteLocation`: a concurrent soft-delete does not stop the update's write, so the racing update's new content silently lands on an already-deleted row.** Driven through the real `routes.Routes(am)` mux behind `httptest.NewServer`, two real `*http.Client` requests fired concurrently per iteration — `PATCH /assets/{assetID} {"name":"raced-update"}` racing `DELETE /assets/{assetID}` on the same freshly-created asset (and separately, `PATCH /locations/{locationID}` racing `DELETE /locations/{locationID}`). Both `asset.go`'s `UpdateAsset` and `location.go`'s `UpdateLocation` read the current row through `GetAsset`/`GetLocation` (`WHERE id = ? AND deleted = false`) but then write through a bare `Updates(map[string]any{...}).Where("id = ?", id)` with **no `deleted` guard on the write at all** — so a `DeleteAsset`/`DeleteLocation` that flips `deleted=true` in the gap between the update's own read and its own write is invisible to that write, which still applies the caller's new Name and returns HTTP 200/nil-error. Repeated across 200 fresh rows per entity: Asset — 197-199/200 iterations landed both PATCH and DELETE as success, and in every one of those the persisted row was confirmed `deleted=true` with `name="raced-update"` (read via a raw `SELECT`, since `GetAsset`/`ListAssets` would filter the row out and report nothing). Location — 199/200 iterations, 199/199 of those confirmed the same shape. This race is far wider than A13's (no extra work happens between the delete's own read and write, unlike `CommitHold`'s `PostMovement` detour), which is why it reproduces on almost every iteration rather than roughly half. **Fix location**: give both `UpdateAsset`'s and `UpdateLocation`'s writes a compare-and-swap guard — `Updates(...).Where("id = ? AND deleted = ?", id, false)`, checking `RowsAffected` and returning `ErrAssetNotFound`/`ErrLocationNotFound` on 0 rows affected — the same shape already recommended for A13 and already used by `mwanachama-backend-git`'s `advanceBranchHead`. | 📋 | Found 2026-09-19 by the fleet integration-test sweep (loophole catalogue #8/#2: a second actor deleting while the first is mid-update; a derived/soft-delete state one write path checks and another ignores). Two pinning tests committed in `routes/a14_update_delete_race_test.go` (`TestPinsA14_UpdateAssetCanWriteIntoAnAlreadyDeletedRow`, `TestPinsA14_UpdateLocationCanWriteIntoAnAlreadyDeletedRow`) asserting the *current* broken behavior (at least one of 200 iterations lands a racing update's content on an already-deleted row) — each fails loudly if the race stops reproducing, and each documents in its own comment what to flip the assertion to once A14 lands (0 iterations). Widening note: the same shape was also found and filed in `mwanachama-backend-taskmanager` as W19 (`UpdateTask`/`DeleteTask`, same session); `mwanachama-backend-actor` was checked and ruled out (no `DeleteGroup`/`DeleteActor` method exists at all, so there is nothing for an edit to race — see that repo's own sweep log). `go test ./...` and `go test -tags=integration ./...` both green with these added. |
